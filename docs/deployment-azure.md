# AppSec Scout — Dual Deployment Strategy (Local Docker + Azure)

> **Status: proposal.** This document is a recommendation, not a description of implemented
> behavior — unlike the other files in `docs/`. Nothing here is built yet. It exists to record the
> target architecture and the sequenced work needed to reach it, so implementation can proceed as a
> normal epic/story series (see [CLAUDE.md](../CLAUDE.md#story-writing)) without re-deriving the
> analysis each time.

## Goal

Run AppSec Scout in two parallel, independently supportable tracks, sharing the same application
code and container images:

1. **Local Docker** (existing, unchanged) — an operator clones the repo and runs
   `scripts/appsec-scout.ps1` on their own machine, exactly as documented in
   [docs/install.md](install.md).
2. **Azure** (new) — the same `appsec-scout` and `dependency-track` images run as managed Azure
   services, provisioned and deployed via Terraform, orchestrated by Azure DevOps pipelines.

Neither track should regress the other. The dividing line is **infrastructure, not application
code**: the Laravel app should not know or branch on which track it is running in. Everything that
differs between the two must be expressed as environment/config/secret input, the same way the app
already lets `DB_CONNECTION`, `SESSION_DRIVER`, `CACHE_STORE`, and `QUEUE_CONNECTION` vary today.

## What Already Works In Both Tracks

The codebase is closer to cloud-ready than a fresh assessment might suggest:

| Concern | Current state | Azure fit |
| --- | --- | --- |
| Database | `DB_CONNECTION`/`DB_HOST`/... fully env-driven, MySQL 8 in both Docker and CI-sqlite | Azure Database for MySQL Flexible Server — drop-in, no code change |
| Session/Cache/Queue | All three already default to `redis` via env (`config/session.php`, `config/cache.php`, `config/queue.php`) | Azure Cache for Redis — drop-in |
| Credential storage | Centralized, encrypted `credentials` table (`App\Credentials\Vault`, `Credential::$casts['value']`) — no credential ever touches the host filesystem | Works unchanged; only the encryption key (`APP_KEY`) needs a new source, see below |
| Container hardening | `app` and `dependencytrack-bootstrap` already run as non-root, read-only rootfs, capabilities dropped, writable paths explicit | Directly portable to Container Apps/AKS security context |
| Object storage abstraction | `config/filesystems.php` already declares an `s3` disk (unused, `default` is `local`) | Confirms the app was already written against Laravel's disk abstraction, not raw `storage_path()` calls, in most places |
| Image build | `docker/Dockerfile` (app) and `docker/ops/Dockerfile` (ops) are already multi-stage, proxy/CA-aware builds producing a single runtime image | Same image can be pushed to ACR and run in Container Apps/AKS with no rebuild logic change |

This means the Azure work is almost entirely **new infrastructure plus a handful of targeted app
changes**, not a rewrite.

## Gaps To Close Before An Azure Deployment Is Safe

### 1. `APP_KEY` bootstrap is single-host-volume-shaped (critical)

`docker/entrypoint.sh` generates `APP_KEY` on first boot and persists it to
`storage/app/private/.env` on the `app_storage` named volume; every subsequent boot copies it back.
This is fine on one Docker host with a durable volume. It is **actively dangerous** in Azure
Container Apps/AKS, where replicas are ephemeral and revisions can be recreated without their
previous writable layer: a fresh container with no matching persisted volume would silently
generate a **new** `APP_KEY`, which immediately makes every row in the `credentials` table
undecryptable (`Vault::credentialValue()` already fails closed — returns `null` — on
`DecryptException`, so this fails as silent credential loss, not a crash), invalidates every active
session, and breaks the 2FA/recovery-code encrypted columns.

**Recommendation**: for the Azure track, `APP_KEY` must be supplied externally (Azure Key
Vault → Container Apps secret reference / managed identity), never generated by the entrypoint.
Gate the existing generate-and-persist block behind an explicit flag (e.g. skip it whenever
`APP_KEY` is already present in the environment) so the local Docker flow is untouched.

### 2. SBOM/Static-Analysis upload path assumes ops and app share a Docker host (the "not sure how yet" question)

Today, `invoke-ops.ps1 -SbomScan`/`-StaticAnalysis` runs the `ops` container, writes reports to
`SBOM_OUTPUT_DIR`/`STATIC_ANALYSIS_OUTPUT_DIR` on the **host**, and that same host directory is
bind-mounted read-only into the `app` container (`docker-compose.yml`) as
`/var/www/html/sbom-import` / `/var/www/html/static-analysis-import`. `PendingSbomScanImporter`/
`PendingStaticAnalysisScanImporter` then read `run.jsonl` plus the referenced report files straight
off that mount, on a per-minute scheduler tick, tracking progress with a cursor file
(`config/sbom.php` / `config/static_analysis.php`).

This whole pipeline depends on ops and app being **bind-mount siblings on the same host filesystem**
— which is exactly the case that breaks once `appsec-scout` runs in Azure and `invoke-ops.ps1`
keeps running on the admin's own machine as you described. There is no shared filesystem to mount
across that boundary.

**Recommendation**: add a new, authenticated HTTP ingestion path, additive to the existing one
(local Docker keeps using the bind-mount pipeline unchanged; it is simpler and has no network
dependency, so there's no reason to force it through HTTP too):

- Add `laravel/sanctum` (first-party Laravel package — flagging per CLAUDE.md's "no new
  dependencies without explicit approval" rule) for scoped API tokens, issued from a new
  `Admin -> System Credentials`-style screen ("Operations API Tokens"), distinct from human login
  and from the existing Source/Tracker/Source-Control credentials.
- Add a new route, e.g. `POST /api/ops/sbom-scans` and `POST /api/ops/static-analysis-scans`,
  `auth:sanctum` + a dedicated ability/permission (not `admin.queue` — a narrower
  `ops.remote-upload` permission), accepting the same per-repository payload
  `collect-sboms.sh`/`collect-static-analysis.sh` already produce (the report files plus the
  `run.jsonl` line describing them).
- The controller calls straight into the existing `AttachmentTargetResolver` +
  `AttachmentService` (the same services `PendingSbomScanImporter` and the
  `assets:import-attachment` Artisan command already use) rather than writing into a directory for
  a cursor-based importer to pick up later — there's no multi-host filesystem to poll, so the
  cursor/polling design doesn't need to be reinvented over HTTP, it can ingest synchronously per
  request.
- `invoke-ops.ps1` gains a new mode (e.g. `-RemoteUrl`/`-ApiToken`, or reads them from
  `docker/ops/.env`) that, when set, POSTs each finished repository's reports to that endpoint
  instead of (or in addition to — see below) writing to the local bind mount. When unset, behavior
  is identical to today.
- Because SBOM/static-analysis scans can run for hours and land results incrementally
  (`docker/ops/collect-sboms.sh` writes `run.jsonl` per repository as it finishes), the remote
  upload should also be incremental — one POST per finished repository, not one bundle at the end
  — to preserve the existing "see results as they land, survive a mid-scan interruption" behavior
  documented in `invoke-ops.ps1`'s own help text.

### 3. Attachment/file storage is local disk

Alert/system/container attachments (`AttachmentService`) and the SBOM/static-analysis import mounts
are local filesystem paths. For Azure, attachments should move to Azure Blob Storage. Laravel's
built-in `s3` disk driver does not talk to Azure Blob natively; the standard, actively maintained
option is `league/flysystem-azure-blob-storage` — again a new dependency requiring explicit
sign-off. Configure it as a new `filesystems.disks.azure` entry, selected via `FILESYSTEM_DISK` in
the Azure track's environment only; `local`/`public` stay the default for Docker Compose.

### 4. One container currently runs web + queue + scheduler together

`docker/supervisord.conf` runs `nginx`, `php-fpm`, `php artisan schedule:work`, and
`php artisan queue:work` in a single container — correct and simple for one Docker host. In
Container Apps/AKS, running multiple replicas of that same image for the web tier would also
multiply the scheduler and queue workers, which is wasteful and, for the scheduler specifically,
redundant work racing on the same per-minute tick (the SBOM/static-analysis importers' cursor
files make concurrent ticks safe, but pointless).

**Recommendation**: for the Azure track only, split into three workloads from the same image:
a web replica set (nginx+php-fpm, horizontally scalable), a single queue-worker replica or Container
Apps job, and a single scheduler replica or a Container Apps **scheduled job** running
`php artisan schedule:run` on a cron trigger instead of `schedule:work` looping in-process. Local
Docker keeps the current all-in-one Supervisor container unchanged.

### 5. Dependency-Track/Trivy state and sizing

`dependencytrack-postgres`, `dependencytrack-apiserver` (JVM heap tuned via `DTRACK_JAVA_MAX_HEAP`
against the *local host's* available memory), and `trivy-server` (persistent vulnerability DB cache
in the `trivy_data` volume) all assume durable local volumes and hand-tuned local resource limits.
For Azure: Azure Database for PostgreSQL Flexible Server for Dependency-Track's DB, persistent
storage (Azure Files or a managed disk, depending on Container Apps vs. AKS) for `trivy_data`, and
JVM heap/CPU sized from the target SKU rather than the current `.env.example` defaults.

### 6. Secrets model

The two-`.env`-files model (`/.env` for Compose, `app-laravel/.env` for Laravel, each documented in
[docs/install.md](install.md#two-env-files)) is Compose-specific. The Azure track needs its secrets
(`DB_PASSWORD`, `APP_KEY`, `DTRACK_ADMIN_PASSWORD`, proxy/TLS material if applicable, etc.) sourced
from Azure Key Vault and injected as Container Apps secret references / managed-identity-scoped
access — never committed, never baked into the image, never passed as plain Terraform variables in
source control.

## Proposed Repository Layout (additive only)

Nothing under `/scripts`, `/docker`, `docker-compose.yml`, or `docs/install.md` needs to change for
this — the Azure track is new, parallel material:

```
/infra/azure/
  terraform/
    modules/
      network/              # VNet, subnets, private endpoints/DNS zones
      acr/                  # Azure Container Registry
      keyvault/              # Key Vault + access policies / RBAC
      mysql/                # Azure Database for MySQL Flexible Server
      redis/                # Azure Cache for Redis
      postgres/              # Azure Database for PostgreSQL Flexible Server (Dependency-Track)
      appsec-scout-app/      # Container Apps env + app/queue/scheduler workloads
      dependency-track/      # Container Apps/AKS workloads for apiserver/frontend/trivy
      monitoring/            # Log Analytics, diagnostic settings, alerts
    environments/
      dev/
      prod/
  pipelines/
    azure-pipelines-plan.yml   # terraform plan on PR-equivalent trigger
    azure-pipelines-apply.yml  # terraform apply on merge/approval, per environment
    azure-pipelines-image.yml  # build docker/Dockerfile, push to ACR, tag per commit
```

`docs/deployment-azure.md` (this file) becomes the entry point; once implemented, split it the way
`docs/architecture.md`/`docs/install.md`/`docs/operations.md` are split, and update its status
banner from "proposal" to "implemented".

## CI/CD Split

The existing `.github/workflows/laravel-ci.yml` stays exactly what it is: the PR-merge quality gate
(Pint, PHPStan, Pest, composer audit) for the application code, regardless of where it eventually
runs. It does not build or publish a container image today, and doesn't need to.

Azure DevOps pipelines are a separate, additive concern layered on top, triggered on pushes to a
deploy branch (or on tags) rather than every PR:

1. **Image pipeline** — builds `docker/Dockerfile`, tags with the commit SHA, pushes to ACR.
2. **Terraform plan** — runs on infrastructure PRs, posts the plan for review.
3. **Terraform apply** — runs on merge to the infra branch, with a manual approval gate for `prod`.
4. **App deploy** — points the Container Apps revision at the newly pushed image tag; migrations
   run as an explicit pipeline step (`php artisan migrate --force` against the target environment),
   not implicitly on every container boot the way the local entrypoint does today, since that
   implicit-migrate behavior is a "friendly first run" convenience for the local track, not
   something a controlled deployment pipeline should rely on.

## Suggested Sequencing (epic/story shape)

Per CLAUDE.md's story-writing rules, this should be one epic ("Enable an Azure deployment track
alongside local Docker") with independent child stories, roughly in this order:

1. Externalize `APP_KEY`/secret bootstrap so it can be supplied instead of generated (gap #1) —
   unblocks everything else; without it no Azure deployment is safe to run twice.
2. Terraform: networking + Key Vault + ACR (foundation, no app changes required).
3. Terraform: Azure Database for MySQL + Azure Cache for Redis.
4. Add Azure Blob Storage disk for attachments (gap #3) + Terraform storage account module.
5. Split web/queue/scheduler workloads for the Azure track (gap #4).
6. Terraform: Container Apps environment running appsec-scout against the above.
7. Terraform: Dependency-Track + Trivy on Azure (Postgres Flexible Server + persistent storage).
8. Azure DevOps pipelines: image build/push, plan/apply, deploy.
9. Add the authenticated remote SBOM/static-analysis upload endpoint + Sanctum tokens (gap #2) and
   the matching `invoke-ops.ps1` remote-upload mode — this is the piece that lets an admin keep
   running `invoke-ops.ps1` locally against an Azure-hosted appsec-scout.
10. Update `docs/install.md`/`docs/operations.md` to cross-reference the new track; flip this
    document's status banner to "implemented" and split it per the existing docs/ conventions.

Story 1 and story 9 are the two changes that touch application code paths used by both tracks
(entrypoint bootstrap, and the ops upload flow); everything else is new, isolated infrastructure or
new isolated code paths gated by environment, so the local Docker experience in
[docs/install.md](install.md) keeps working exactly as documented throughout.
